# MedB Integrations (M0)

> **Status: implementation notes, not specification.** This describes the
> integrations layer added on 2 Oct 2026 at Gem's request (DECISIONS D-72 to
> D-75), and live account sync added on 3 Oct 2026 on Gem's F-26 ruling (D-76
> to D-78, section 5). Where it touches a constitutional question, the question
> is logged as a finding (F-22 to F-27, F-28 to F-35) and **not** decided here.
> Rev 1.0 governs.

## Ground rules
Every integration follows the same rules as the rest of M0:

| Rule | How it applies here |
|---|---|
| Off by default | `config/default.json` → `integrations.{mcp,importers,outbox,sync}.enabled: false` (and every sync service off). Switch on locally in `data/integrations.json` (gitignored), which `python3 -m medb.api` and the MCP server merge over the defaults. |
| Local-first (Principle 8) | Importers read local files only. The MCP bridge, the outbox webhook and the OAuth redirect listener talk to loopback only. **The one exception is live account sync (section 5, Gem's F-26 ruling):** a declared `live_sync` outbound class, HTTPS only, to a fixed per-provider host allowlist, only for services the user enabled and connected. |
| Default deny | Unknown file formats, paths outside the import roots, non-loopback URLs, and MCP actors other than `agent:*` / `inference:*` are all refused. |
| One mechanism | Every entry point is an `@reaches` interface or a registered route/external interface. It shows up in `interface_inventory()`, is refused with 423 while a reached primitive is suspended, and is logged. |
| Self-description | `self_description()["integrations"]` reports each integration's live status, actor and last activity. `self_description()["network"]` lists the two loopback client modules, generated by `netscan` (D-68). |
| No new authority | No integration can do anything its actor could not already do through the API. |

New primitives: `integrations.import` (depends on `corpus.ingest`), `integrations.outbox` (on `governance.log`), `integrations.mcp` (on `governance.log`), and `integrations.sync` (on `corpus.ingest`).

## 1. MCP server for AI assistants (D-74)
`medb/integrations/mcp_server.py` speaks the Model Context Protocol over stdio, one JSON-RPC 2.0 message per line, stdlib only.

**It holds no database handle.** Each tool call becomes exactly one HTTP request to the local MedB API, carrying:
- the bearer token of the configured actor;
- `X-MedB-Via: mcp`;
- the tool name.

The API then applies its normal rules (auth, 423, user-only checks, logging) and three MCP checks:
1. the integration is enabled;
2. the token's actor is the configured MCP actor for that tool;
3. the tool belongs to that route.

Each call is recorded in the hash-chained `integration_activity` stream. That stream is not cross-linked into gov, so Q-1 evidence is unperturbed.

A separate process sharing the SQLite file was rejected. Two writers would race on the hash-chain heads (`EventStore.append` reads the head and then inserts).

| Tool | Route | Plane |
|---|---|---|
| `medb_q1_<query>` (×8) | `GET /api/q1/<query>` | audit |
| `medb_build_context_package` | `POST /api/context/build` | capability |
| `medb_propose_inference` | `POST /api/claims/propose` (`inference:*` token) | capability |
| `medb_submit_delegation_action` | `POST /api/delegation/evaluate` (agent forced to the MCP actor) | capability |
| `medb_list_open_escalations` | `GET /api/view/escalations` | audit |

**What the assistant can never do.** It cannot assert user self-accounts, confirm or reject claims, grant or revoke permissions or delegations, resolve escalations, withdraw corpus items, or import files. This is enforced three ways:
- No tool exists for any of these.
- The MCP actor is refused at configuration if it is `user`, `reader`, `system`, `environment`, `auditor:*` or `appointer:*`.
- The agent/inference token would get 403 from the API anyway. Inference tokens may use only the propose route plus the audit plane.

**Suspensions.** A suspended `integrations.mcp` blocks the bridge's capability tools. Its audit tools stay open, as the audit plane always does (D-11/F-11). Whether an outside assistant may act as an *inference* actor is F-23.

### Connecting an assistant (Cursor, Codey or any MCP client)
1. Create `data/integrations.json`:
   ```json
   {"integrations": {"mcp": {"enabled": true, "actor": "agent:assistant",
                             "inference_actor": "inference:assistant",
                             "api_url": "http://127.0.0.1:8765"}}}
   ```
2. Restart `python3 -m medb.api`. With MCP enabled it adds tokens for `agent:assistant` and `inference:assistant` to `data/api_tokens.json`. Existing tokens are never changed.
3. Point the client at the launcher. For Cursor, use `~/.cursor/mcp.json` or `.cursor/mcp.json` in a project:
   ```json
   {"mcpServers": {"medb": {"command": "python3",
                            "args": ["/workspace/medb/tools/medb_mcp.py"]}}}
   ```
   Other clients (Codey etc.) take the same command and args in their MCP server settings. To avoid reading the token file, pass `MEDB_MCP_TOKEN` / `MEDB_MCP_INFERENCE_TOKEN` in the client's `env`.
4. The assistant now sees the 12 `medb_*` tools. Give it a delegation grant (Delegation screen) and use/infer grants (Permissions) only if you want its actions or packages to succeed. Without grants, everything is refused or escalated, and logged.

The launcher refuses to start (exit 2, message on stderr) if the integration is off, the actor is not allowed, or `api_url` is not `http://127.0.0.1:<port>`.

## 2. File importers into the corpus (D-72)
`Importer.import_file(path, actor, fmt=None, scope=None, source=None, sensitivity=None, account=None)` reaches `integrations.import`, `corpus.ingest` and `permissions.closure`. It is also exposed as `POST /api/import/file`, and in the app's Integrations screen.

**Checks, in order:**
1. **User-only.** Anyone else is refused and logged as `PROHIBITED_ATTEMPT`.
2. **Enabled.** If the importers are off, the run is refused and logged as `IMPORT_REFUSED`.
3. **Path.** After resolving symlinks, the path must be under `allowed_roots` (default `imports/` in the repo).
4. **Size.** The file must be within `max_file_mb`.
5. **Format.** It must be recognised by extension *and* content sniff; a format the user names explicitly must match the sniff. Anything else is refused (default deny).
6. **Ingest grant.** An active grant must cover the source (default `import:<format>`), scope and sensitivity (default **high**). This is checked **before** the file is read.

**What it writes:**
- The run streams the file and ingests one corpus item per record.
- Each item carries `provenance`: importer version, run id, format, export kind, file name, **file SHA-256**, source-account label, record index and reference, a `third_party_content` flag, and format details (FHIR resource ids and subject, mail labels, cookie counts).
- One `IMPORT_RUN` gov entry summarises the run.
- Items are ordinary corpus items. Use needs a use grant (D-71), and the user can withdraw them (F-05). There is no erasure.

| Format id | Source material |
|---|---|
| `text_note`, `json_records`, `ndjson_records`, `csv_rows` | Markdown/plain notes; JSON, NDJSON or CSV records |
| `fhir_r4_bundle` | Patient-held FHIR R4 Bundle. Observation, Condition and MedicationStatement become items; other resource types are counted and skipped. No reference is ever fetched. |
| `gmail_mbox` | Google Takeout Mail `.mbox`, streamed. Headers plus the text body; attachments are counted, not imported. |
| `chrome_history_takeout`, `chrome_bookmarks_html`, `chrome_bookmarks_json` | Takeout Chrome history JSON, bookmarks HTML, or a profile `Bookmarks` file |
| `calendar_ics`, `contacts_vcf` | Takeout Calendar `.ics` and Contacts `.vcf`, streamed |
| `github_json` | GitHub account export files (`repositories_000001.json`, …) or repo metadata JSON |
| `facebook_json` | Facebook "Download your information" JSON (posts, messages; mojibake repaired) |
| `chrome_history_sqlite`, `firefox_places_sqlite` | A *copy* of a profile's `History` / `places.sqlite`, opened read-only and immutable |
| `chrome_cookies_meta`, `firefox_cookies_meta` | **Cookie metadata only**: per domain, a count, first set and last accessed |

**Cookies.** Cookie values are live login credentials, so they are never imported. The SQL selects only host and time columns; `name`, `value` and `encrypted_value` are never read. Tests check that a known cookie value and name appear nowhere: not in the database file, the gov log, the export, the outbox or `self_description`.

**Streaming.** These formats are streamed: mbox, CSV, NDJSON, ICS, VCF, bookmarks HTML, and SQLite cursors. JSON documents are parsed whole, bounded by `max_json_mb`. Item content is clipped at `max_item_chars`, and a run stops at `max_items_per_run` (`truncated_at_max_items`).

**Open questions.** Whose data is the third-party content inside these exports (F-24)? Whether imported records count as self-accounts or as external sources is F-22, and how much the provenance can be trusted is F-27.

## 3. Local notification outbox (D-73)
`Outbox.sync()` (`integrations.outbox`, `governance.log`) scans gov entries it has not yet seen. For each new escalation, suspension, breached obligation or inference proposal awaiting review, it appends one `NOTIFY` event to the hash-chained `outbox` stream.

- **No content.** Notifications carry kinds, ids, times and a fixed title, never claim or corpus content.
- **When it runs.** Sync is idempotent and runs after each API write and when the feed is viewed.
- **Evidence unperturbed.** The outbox is not cross-linked into gov.
- **Webhook.** Optional and off even when the outbox is on. It POSTs each notification to `http://127.0.0.1` or `http://[::1]` only; anything else is refused at send time without a connection. Each result is recorded as `DELIVERY`. Failures are recorded and never break the request.
- **Suspended outbox.** A suspended `integrations.outbox` stops sync. The feed (audit plane) stays readable.
- **Open question.** Whether a notification is itself a "MedB output" for Principle 12 is F-25.

## 4. App: Integrations screen
The screen shows:
- one card per integration: enabled or disabled, actor, last activity, and configuration problems;
- the notification feed, with links to the relevant screens;
- import runs, including refusals;
- **live account sync**: one row per service with enabled/connected, account, last sync, item count, last run counts and error, hosts, and (user token only) *Connect…* / *Sync now* / *Disconnect* buttons plus *Sync all connected* (section 5);
- recent MCP calls;
- for the user token only, the importer: a file picker over the import roots, format (auto or named), scope, source, sensitivity and account label, with a confirmation dialog.

## 5. Live account sync (D-76 to D-78)
Gem decided F-26 on 3 Oct 2026: build live sync, keep the file importers as the fallback. Later that day Gem removed Facebook from live sync (D-79), so the providers are Google, GitHub and local browser profiles. `medb/integrations/livesync.py` (`SyncManager`), `sync_http.py` (the only outbound HTTP code), `oauth.py` (flows and the loopback listener) and `sync_tokens.py` (local token store).

| Service id | Provider | What is synced | Incremental by | Default scope |
|---|---|---|---|---|
| `google_gmail` | Google | Messages (raw RFC 822 → same parser as the mbox importer), labels | Gmail `historyId` (`history.list`; 404 → full re-list) | `correspondence` |
| `google_calendar` | Google | Primary-calendar events (cancelled → deletion) | Calendar `syncToken` (410 → full resync) | `calendar` |
| `google_contacts` | Google | People API connections (names, emails, phones, orgs, birthdays, notes) | People `syncToken` | `contacts` |
| `github` | GitHub | Profile, repos, starred, public events, issues/PRs involving you | `since` (issues), ETag (events), item version (repos, stars) | `code` |
| `chrome_local` | local | `History` (urls), `Bookmarks`, `Network/Cookies` **metadata** | last visit time; item version | `browsing` |
| `firefox_local` | local | `places.sqlite` (history, bookmarks), `cookies.sqlite` **metadata** | last visit date; item version | `browsing` |

Chrome Sync has no public API for history, so Chrome and Firefox are read **live from the local profile**: the files (plus `-wal`/`-shm`) are copied to a fresh `0700` temp directory, opened `mode=ro`, and the copy is deleted after every run. The browser's own files are never opened for writing (a test compares them byte-for-byte).

### How the local-first rule is kept
- **One outbound class, declared.** `netscan` lists `medb.integrations.sync_http` as `direction: outbound`, `class: live_sync`, with its `allowed_hosts`, the services enabled now and `hosts_in_use`. `outbound_enabled` turns true only when a service is enabled. `self_description()["integrations"]["live_sync"]` reports the same, plus each service's status. Nothing else in MedB gained network code (the AST scan test pins the module list).
- **Fixed allowlist, HTTPS only, checked before connecting.** Google: `accounts.google.com`, `oauth2.googleapis.com`, `gmail.googleapis.com`, `www.googleapis.com`, `people.googleapis.com`. GitHub: `github.com`, `api.github.com`. A URL for another host, another provider's host, `http:`, a non-443 port or embedded credentials raises `HostNotAllowed` before any socket exists. The list is code, not config, so a config file cannot widen it. Redirects are never followed. Pagination links (GitHub `Link: rel="next"`) are re-checked against the allowlist.
- **Only the provider's API.** MedB sends OAuth requests and read-only API calls carrying the user's own token. It never sends corpus, claim or governance content anywhere. Sync runs in the local API process and lands only in the local corpus.
- **Off by default; the user opts in per service.** Both `integrations.sync.enabled` and `services.<id>.enabled` must be true, and the user must then connect the service.

### Tokens and OAuth apps
- **You register your own OAuth apps** (steps below). MedB ships no client ids. Ids and secrets go in `data/sync_clients.json` (gitignored), never in the config, because the config is recorded at GENESIS and exported.
- **Tokens** are stored in `data/sync_tokens/<provider>.json` (directory `0700`, files `0600`, gitignored). They are **not encrypted** (finding F-29): the standard library has no encryption, and M0 does not invent crypto. An OS keyring is the obvious upgrade.
- **Tokens never appear** in the database, the gov log, exports, the outbox, `self_description`, status/run responses or logs. Tests plant access tokens, a refresh token, client secrets and a device code, run every flow (including refresh and error paths), then search all of those for them.
- **Read-only scopes only.** `gmail.readonly`, `calendar.readonly`, `contacts.readonly` (+ `openid email` to name the account); GitHub `read:user`. If a provider grants anything outside this set, the token is refused and not stored (`scope_not_read_only`).
- **Disconnect** (user only) deletes the local token file. It optionally asks Google to revoke it; for GitHub, revoke the app yourself at github.com → Settings → Applications. One Google token serves all three Google services, so disconnecting any one of them disconnects all three. Disconnect is on the **revocation plane**: it stays possible while `integrations.sync` is suspended, because it only removes capability.

### What every synced item carries
- **Ordinary corpus items.** Ingested through `Corpus.ingest` with source `sync:<service>`, the service's scope, sensitivity **high**. An active `ingest` grant must cover all three; this is checked before any API call. Use needs a use grant (D-71). You can withdraw items; there is no erasure.
- **Provenance.** `service`, `provider`, `account_id`, API `endpoint`, `remote_id`, `version` (etag / history id / updated time), `run_id`, `response_sha256`, `supersedes_corpus_id`, and `third_party_content`.
- **Idempotent.** A remote object whose version is already in the corpus is skipped. A changed version is ingested as a new item naming the one it supersedes.
- **Remote deletions are recorded, never applied.** Each one is a `REMOTE_DELETION` event in the `sync` stream plus a `SYNC_REMOTE_DELETION` notification. Nothing is erased or withdrawn automatically (F-32).
- **Run records.** Every run is a `RUN` event in the hash-chained `sync` stream, mirrored into gov. It records counts (`ingested`, `updated`, `unchanged`, `remote_deletions`, `third_party`), the grant, the error if any, and the cursor. A failed or truncated run (`max_items_per_run`) does not advance the cursor, so the next run picks up the rest.

### Who can do what
- **Connect, sync now and disconnect: the user token only.** `agent:*`, `inference:*`, the MCP actors, `reader`, `auditor:*` and `system` are refused and logged (`PROHIBITED_ATTEMPT`). There is no MCP tool for sync, and the user's own token sent through the MCP bridge header is refused too.
- **Scheduled sync** runs as `system`, on your standing configuration, and only for services you connected.
- **Suspensions.** Connect, connect-poll and run reach `integrations.sync` and get 423 while it, or `corpus.ingest` (for runs), is suspended. Audit reads stay open.

### Scheduling (optional, off by default)
- **Inside the API.** Set `integrations.sync.schedule` to `{"enabled": true, "interval_minutes": 60}`. The API then serves requests one at a time and runs due syncs on the same thread in between, so a long sync delays requests while it runs.
- **From cron.** Run `python3 tools/medb_sync.py run --all` (status: `python3 tools/medb_sync.py status`). It talks only to the local API with your user token (`--token`, `$MEDB_USER_TOKEN`, or `data/api_tokens.json`). Example crontab line: `0 * * * * cd /workspace/medb && python3 tools/medb_sync.py run --all >> data/sync_cron.log 2>&1`.

### Setting it up (what you do)
**0. Turn on the services you want.** Create or extend `data/integrations.json`, enabling only what you want:
```json
{"integrations": {"sync": {"enabled": true,
  "services": {"google_gmail": {"enabled": true}, "google_calendar": {"enabled": true},
               "google_contacts": {"enabled": true}, "github": {"enabled": true},
               "chrome_local": {"enabled": true, "profile_path": "~/.config/google-chrome/Default"},
               "firefox_local": {"enabled": true, "profile_path": "~/.mozilla/firefox/<xxxx>.default-release"}}}}}
```
Restart the API: `python3 -m medb.api`.

**1. Grant ingest for each source.** (Optional: set `"source": "sync:google"` on the three Google services so one grant covers them; a source must start with `sync:`. The status route reports each service's `source`, `client_missing` field names and `connectable`.) On the Permissions screen, give one ingest grant per service: source `sync:<service>`, that service's scope (`correspondence`, `calendar`, `contacts`, `code`, `social`, `browsing`), sensitivity max **high**. Without a grant, sync is refused before any API call.

**2. Google (Gmail, Calendar, Contacts).**
1. In [Google Cloud console](https://console.cloud.google.com/), create a project.
2. Enable the **Gmail API**, the **Google Calendar API** and the **People API** (APIs & Services → Library).
3. Set up the OAuth consent screen (Google Auth Platform): user type **External**. Add your own Google address under **Test users**, and add the scopes `.../auth/gmail.readonly`, `.../auth/calendar.readonly`, `.../auth/contacts.readonly`. Leave it in **Testing**. Gmail read scopes are "restricted", and publishing would need Google's security assessment; in Testing mode refresh tokens expire after 7 days, so you reconnect weekly (F-31 covers provider limits).
4. Create credentials → **OAuth client ID** → application type **Desktop app**. Copy the client ID and client secret. For desktop apps the secret is not confidential, but MedB keeps it in the gitignored file anyway.
5. Put them in `data/sync_clients.json`:
   `{"google": {"client_id": "….apps.googleusercontent.com", "client_secret": "GOCSPX-…"}}`
6. In MedB → Integrations → Gmail → **Connect…** → **Open google sign-in**, then approve. Google redirects to `http://127.0.0.1:<random port>/` on this machine (loopback + PKCE). The dialog shows *Connected as google:you@…*. One connection covers all three Google services.

**3. GitHub.**
1. github.com → Settings → Developer settings → **OAuth Apps** → *New OAuth App*. Use any name, homepage `http://127.0.0.1:8765/` and callback `http://127.0.0.1/` (unused by the device flow).
2. In the app's settings, tick **Enable Device Flow**. Copy the **Client ID**; no secret is needed.
3. Add `{"github": {"client_id": "Ov23…"}}` to `data/sync_clients.json`.
4. In MedB → GitHub → **Connect…**: open `https://github.com/login/device`, enter the code shown, and approve. Scope is `read:user` only, so private repositories are not visible (F-28).

**4. Chrome / Firefox (local, no account).**
1. Set `profile_path` as in step 0. For Chrome on Linux this is usually `~/.config/google-chrome/Default`; on macOS `~/Library/Application Support/Google/Chrome/Default`. For Firefox, see `about:profiles` → *Root Directory*.
2. Click **Connect…** (this only checks the directory), then **Sync now**. Nothing goes over the network. Set `"cookies": false` on the service to skip cookie metadata entirely.

**5. Sync.** Use **Sync now** per service, **Sync all connected**, `tools/medb_sync.py`, or turn on the schedule.

**Open questions.** F-28 (GitHub scopes), F-29 (token storage), F-30 (other people's data pulled live), F-31 (Google API limits; its Facebook part is moot since D-79), F-32 (remote deletions vs no erasure), F-33 (consent for continuous collection), F-34 (unverified account identity), F-35 (secrets inside synced URLs and mail).
