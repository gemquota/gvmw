# Implementation Decisions and Constitutional Findings (M0)

This file records every implementation choice made in building the M0
substrate. It also flags each point where implementing would have required
resolving an open constitutional question.

* **D-xx** entries are *implementation decisions*. They are the builder's
  readings, they are not part of the spec, and the user can overturn any of them.
* **F-xx** entries are *findings*: places where the spec as available to this
  build does not settle a question. **None of them has been silently
  resolved.** Each states what M0 does for now, chosen to be conservative or
  reversible, and why that is not a resolution.

The authoritative spec (Rev 1.0) was **not available** to this build. Only a
brief was available, condensed in `SPEC_SUMMARY.md`. Only **Section III.1** is
known by number. Findings that might belong to other Section III questions are
marked **"III-mapping: unknown"** and must be checked against Rev 1.0.

---

## A. Implementation decisions

### Platform and storage
* **D-01 Stack.** Python 3.13, standard library only. Runtime storage is SQLite; export is JSON/JSONL. pytest runs from the project venv `.venv/`, because the system Python is externally managed (PEP 668). No network code exists anywhere in the substrate, which serves Principle 8 (local-first). *Update 2 Oct 2026 (Gem's ruling on F-13):* **one exception**: `medb/anchoring.py` may send a single SHA-256 digest of the stream heads to an RFC 3161 timestamping authority. It is off by default, never called implicitly, and is the only module allowed to import network code (a test enforces this). The inbound loopback API (D-55) is not outbound network code. See D-62.
* **D-02 Event sourcing.** Every store is an append-only *stream*: `gov`, `claims`, `permissions`, `policy`, `suspension`, `corpus`, `delegation`. *(Update 2 Oct 2026: also `normative` (D-30/F-18), `auditlog` (D-66/F-11) and `anchors` (D-62/F-13).)* State is always derived by replaying events, with no mutable caches. This trades performance for correctness and auditability, which is acceptable for M0.
* **D-03 Append-only enforcement.** SQLite triggers abort any `UPDATE` or `DELETE` on `events`. Erasable claim content is kept in a separate `content` table, which allows deletion but not update.
* **D-04 Tamper evidence.** Each stream is a **linear hash chain**: `sha256(canonical({prev, record}))`. This is the simplest member of the Crosby & Wallach family; their Merkle *history tree*, with efficient membership and incremental proofs, is not implemented. Every domain event is also cross-linked into the `gov` chain (`STATE_TRANSITION`, carrying `{stream, seq, event_hash}`). `integrity_check()` re-verifies every chain. See F-13 for the limits of this. *Update 2 Oct 2026 (Gem's ruling on F-13):* heads can now optionally be witnessed externally (D-62).
* **D-05 Time.** Timestamps are UTC, ISO-8601 with microseconds, and lexically sortable. The ledger is **bitemporal**: `ts` is transaction time, which answers "what did MedB record then?" (`as_of`), and `temporal_validity` is valid time (`valid_at`). Tests and subjects use an injectable `FixedClock`.
* **D-44 Identifiers.** IDs are random. When a seed is supplied they are deterministic, so subject runs are reproducible.

### Claim ledger
* **D-06 Content vs metadata.** *Content* means `subject, predicate, object, source, temporal_validity`. It is stored under a **salted** commitment (`c-` + sha256(salt + canonical(content))). Because of the salt, a destroyed low-entropy claim, such as a diagnosis name, cannot be recovered by brute-forcing its hash. *Metadata* is kept permanently: `claim_id, origin, created_at, confirmation, scope, sensitivity, derived_from`, transitions, and commitments.
* **D-07 Transitions.** The ledger supports these transitions:
  * `ASSERT`: a user self-account.
  * `PROPOSE`: from inference only.
  * `CONFIRM`, `REJECT`.
  * `CORRECT`: same `claim_id`, `version` + 1, with the old version still visible via `as_of`.
  * `SUPERSEDE`: links two distinct claims.
  * `DISAVOW`: content is kept; the status records that the user no longer endorses the claim.
  * `DELETE`: destroys the content of **every** version and keeps the fact of deletion.

  Every transition except `PROPOSE` is reserved to actor `user`. Attempts by other actors are refused **and** logged as `PROHIBITED_ATTEMPT`. This is how "inference proposes, never promotes" is enforced.
* **D-45 Deletion vs "what then".** After a deletion, `as_of(t)` for a time before the deletion returns the claim's metadata with `content_destroyed: true`, not the old content. The spec requires that deletion destroy content, so recoverability gives way to deletion here. This is a direct reading of the spec, not an open question.
* **D-46 Origin and confirmation vocabulary.** `origin` is `user_stated` or `inference`. `confirmation` is one of `user_asserted`, `unconfirmed`, `user_confirmed`, `user_rejected`. When a user `CORRECT`s an inference, its confirmation becomes `user_confirmed` and it is marked `medb_mediated`.
* **D-47 Principle 12 marking.** `CONFIRM` of a MedB proposal is always `medb_mediated: true`, because the user was exposed to MedB's output by construction. `ASSERT` with `exposure_refs` (for example, package ids the user had seen) is also marked. Exposure is self-reported by the caller. M0 does not infer exposure. See F-19.
  *Update 2 Oct 2026 (Gem's ruling on F-19):* **replaced for ASSERT.** An `ASSERT` is `medb_mediated: true` if it cites `exposure_refs`; otherwise it is `medb_mediated: "possibly"` if MedB has produced **any output at all** before it, and `false` only before the first output. "Output" means the first of: a gov entry of kind `CONTEXT_PACKAGE_ISSUED`, `CLAIMS_RETRIEVED`, `ESCALATION_OPENED`, `EXPORT`, `AUTHORITY_CONFLICT_DEFERRED` or `AUTHORITY_UNDERDETERMINATION`; any inference `PROPOSE`; or any `auditlog` entry. That first output is stored as `mediation_basis`. Limitation: Q-1 reads made while nothing is suspended are deliberately unlogged (D-12), so they cannot trigger the mark. In practice this almost never matters, because seeding a ledger already produces outputs. Packages render `possibly` as the suffix ` [MedB-mediation possible]`, configurable as `rendering.possibly_mediated_marker`. The modal-symmetry check strips only the *configured* markers before looking for hedges, never markers reported by a renderer, so a substituted renderer cannot hide a hedge inside a "marker". Export schema: `medb_mediated` ∈ {true, false, "possibly"}.

### Permissions (Principle 6) and composition
* **D-08 Composition Rule.** A composition is authorized only by a **single** grant that covers every component jointly. That grant must also carry `compose: true` in two cases:
  * multi-input inference (any inference with more than one input), and
  * a use package that spans more than one scope.

  Several grants that each cover one component never add up to authorization for the combination. Same-scope packages under one grant are not treated as a "composition" that needs `compose`. That is a reading, recorded here.
* **D-09 Closure.** Permission closure is computed over the full transitive derivation path, including corpus items. A path that includes a **deleted** node makes the derived item unusable: it is excluded from packages and `retrieve` refuses it. The derived item is not itself deleted (see F-06). *Update 2 Oct 2026 (Gem's ruling on F-05/F-06):* a **withdrawn corpus item** (D-64) is treated exactly like a deleted node: its content stays, but any path through it is unusable (`derivation_nodes` flags `withdrawn` and `unusable`; the package boundary counts `derivation_path_includes_withdrawn_corpus_item`). On claim DELETE the user may now also choose to destroy derived inferences (D-65). The default is still unusable-but-kept.
* **D-36 Privacy by default.** The default sensitivity is `high`. With no grant, nothing can be ingested, inferred, modelled or used. Only `user` can grant or revoke permissions.
* **D-37 Corpus.** The corpus is immutable and append-only. Ingest requires an `ingest` grant that covers both the source and the scope. There is no corpus erasure API (see F-05). *Update 2 Oct 2026 (Gem's ruling on F-05):* still no erasure. A user-only `WITHDRAW` was added (D-64).

### Policy and delegation (P-1)
* **D-42 Policy authority.** `policies/*.json` are **genesis inputs** only. After genesis, the `policy` stream is authoritative and versioned. Each version is logged with its full content and digest. Only `user` can create a version. Any other actor gets `NotAuthorized` plus a `PROHIBITED_ATTEMPT` entry citing P-1.7. An agent action of kind `classification_change` or `policy_change` evaluates to **PROHIBITED / P-1.7**.
* **D-26 Lines changed** means the sum over all files in the action, with added and deleted lines counted as one number per file supplied by the caller.
* **D-27 Unclassified modules** are treated as **critical**, which forces escalation (fail-safe, default-deny).
* **D-21 Dependencies.** P-1 says both "must escalate changes to dependencies" and "may add dependencies of ≤3 direct packages, ≤10 MB, non-critical only". M0 reads the more specific permission as governing within its bounds: inside the bounds the result is AUTHORIZED / P-1.3, and outside them it is REQUIRES_ESCALATION / P-1.3. If a critical module is touched, the result is P-1.2.
* **D-25 Reverts (P-1.4).** A revert of the agent's **own** executed change within 24 h is AUTHORIZED / P-1.4 whatever the module class, as written. Reverts of another agent's change, or after 24 h, are evaluated as ordinary changes. Revert lines count toward the cumulative budget.
* **D-28 Cumulative budget (P-1.5).** The budget counts every *executed* change to non-critical modules, including user-approved escalations, emergency fixes and reverts, over the rolling 30 days. It is a prospective check: `used + proposed > 500` gives REQUIRES_ESCALATION / P-1.5 (`budget_review`). Approving a budget review records `BUDGET_REVIEW`, and counting restarts from that point (D-24).
* **D-22 Emergency clause content.** P-1 does not say what an emergency invocation permits beyond normal operation. M0's reading:
  * The per-action scope is **not** widened: the P-1.1/P-1.3 limits and the P-1.2 escalation categories still apply.
  * Emergency fixes are **exempt from blocking** by the cumulative budget, though they are still counted.
  * They open a reporting obligation.

  This reading is encoded as `interpretations.emergency_exempts_cumulative_budget` in `policies/P-1.json`, outside the clause text. See F-09.

  *Update 2 Oct 2026 (Gem's ruling on F-09):* **the first bullet is replaced.** During a valid emergency (P-1.6.1 condition recorded, P-1.6.3 frequency not exceeded), the per-action line limit for **non-critical** modules is `max(P-1.1 max_lines_per_action, P-1.5 max_lines_non_critical − used)`, where `used` is the current P-1.5 window usage. Critical modules and the other P-1.2 categories still escalate. Emergency lines are still counted toward P-1.5. Attenuated grant limits (D-38) still bind. The new reading is `interpretations.emergency_per_action_limit_up_to_remaining_budget` (with a `_ref`).
  * **Retained (builder's reading, flagged for Gem):** the second bullet (an emergency is not *blocked* by an exhausted budget) is kept. When less than 50 lines remain, an emergency fix of ordinary P-1.1 size is therefore still authorized. Gem's ruling raises the ceiling and does not say whether it also lowers it below 50; M0 chose not to lower it. Gem may overturn this by setting `emergency_exempts_cumulative_budget: false`.
  * The C0/F1/F2/F3/U1/X1 subject emergencies are all ≤ 5 lines, so no §6.8 outcome changed.

  *Update 2 Oct 2026 (Gem's ruling on the D-22 judgement call above):* the "retained" bullet is **withdrawn**. There is **no 50-line floor**. During a valid emergency, if the remaining 30-day budget (`500 − used`) is less than the P-1.1 limit of 50 lines, the fix evaluates to **REQUIRES_ESCALATION / P-1.5**, with `review_type: budget_review` and facts `emergency_clause: "P-1.6"` and `remaining_budget`. It is not authorised. This applies to a fix of any size, even 1 line.
  * The check runs after P-1.6.1 (condition recorded), P-1.6.3 (frequency) and P-1.2 (critical modules and other categories still escalate first). It uses the same sequence-constraint hook as P-1.5 (`used + 50 > limit`).
  * When at least 50 lines remain, the limit is still up to the remaining budget.
  * If the user approves, the action executes as `USER_APPROVAL<P-1.5>`, which records `BUDGET_REVIEW` and resets the window baseline (D-28). Because it is then a user-approved action, not an agent emergency invocation, it does not open a P-1.6.2 reporting obligation and does not count toward the P-1.6.3 frequency limit.
  * `policies/P-1.json`: `emergency_below_floor_escalates: true` (with `_ref`). `emergency_exempts_cumulative_budget` is now `false`, since no emergency is authorised beyond the remaining budget.
  * Subject matrix re-run: unchanged.
* **D-23 Emergency preconditions.** The condition (`build_blocked` or `security_issue_open`) must be **recorded by the environment or the user** (`ENV_CONDITION`). Agents cannot set it. Claiming an emergency when the condition is not recorded evaluates to PROHIBITED / P-1.6.1.
* **D-24 Frequency limit.** M0 counts executed P-1.6 invocations in the rolling 60 days. Once there have been 12, the next request evaluates to REQUIRES_ESCALATION / P-1.6.3 (`frequency_review`), and so does every request after it until the user approves the review. Approval records `FREQUENCY_REVIEW`, executes the pending fix, and restarts the count from that point.
* **D-29 Reporting obligation.** Each emergency fix opens an obligation due 60 minutes later. `report_emergency` discharges it. `check_obligations` records `OBLIGATION_BREACHED`. A breach has **no automatic consequence** in M0 (see F-10).
* **D-38 Delegation grants (ocap).** Root grants come only from the user. A holder may *attenuate* its grant to sub-delegate: narrower `max_lines_per_action`, narrower `max_cumulative_lines`, or a subset of `allowed_kinds`. It can never amplify. The ceiling is the parent grant, or P-1 when the parent sets no limit. Revoking or expiring a parent cascades down the chain. With no active grant, the result is PROHIBITED / DELEGATION.grant. An unknown action kind gives PROHIBITED / DELEGATION.default_deny.
* **D-30 Escalations.** Only `user` resolves escalations, and an approval executes the action as `USER_APPROVAL<clause>`.
  * Approval cannot reach PROHIBITED actions, because those never open an escalation.
  * Approval cannot authorize a suspended capability: suspension is checked again at execution time.
  * The user's response is recorded as `directive` claims, scope `authority` (see F-18).
    *Update 2 Oct 2026 (Gem's ruling on F-18):* **superseded.** Each stated position is recorded as a `DIRECTIVE` event in the separate hash-chained **`normative`** stream (`medb/normative.py`, primitive `normative.store`). Every directive is mirrored into `gov` (`STATE_TRANSITION` with `{stream, seq, event_id, event_hash}`), included in export, and checked by `verify_export.py`: each normative event must have a gov cross-link. Directives no longer enter the claims ledger. `ESCALATION_RESOLVED`, `AUTHORITY_*` entries and resolver results carry `directive_ids` instead of `claim_ids`, and CU evidence cites `normative:<id>`. `authority.resolution` now depends on `normative.store` instead of `identity.model`, which is the accurate dependency because the resolver never read the identity model. Suspending `normative.store` therefore suspends `authority.resolution` directly.
  * `deferrable` defaults to true and can be set on the action (see F-02).
    *Update 2 Oct 2026 (Gem's ruling on F-02):* **superseded; see D-63.** An agent can no longer set it.
* **D-43** Recording environment conditions is restricted to `environment` and `user`.
* **D-48** The evaluator is a pure function of the recorded policy and classification, the governance-log history, the recorded environment, and the grant. Each `ACTION_EVALUATED` stores the full clause trace plus the policy and classification digests, so any decision can be replayed.

### Authority (Principle 1, III.1)
* **D-31 Conflict detection.** M0 detects conflict only among positions given **at the same time** (one escalation response). Positions with *distinct user-given priorities* count as ordered by the user, and the highest priority wins (see F-16). Otherwise, distinct positions are handled as follows:
  * If the decision is deferrable, `AUTHORITY_CONFLICT_DEFERRED` is recorded. Nothing happens and the escalation stays open.
  * If it is not deferrable, the outcome is **CONSTITUTIONAL_UNDERDETERMINATION (III.1)**. A suspension is recorded on `authority.resolution:<matter>`, which propagates to `delegation.execution:<matter>`. No tie-break of any kind is applied: not recency, not "safer option", not inaction-as-default. Note that *not acting* is also not chosen as the policy outcome. The action simply cannot proceed under suspension, and the record says so.
* **D-13 Matter-scoped suspension.** Capabilities may be scoped as `primitive:matter`. A record on `x` blocks `x` and every `x:*`. A record on `x:m` blocks only `x:m`. See F-01 for why scoping is itself an interpretation.

### Suspension registry
* **D-10 Immutability vs status.** `RECORD` bodies are never changed, and their `status` field is the status *at creation*. The current status is derived from appended `TRANSITION` events: `SUSPENDED`, then `RESOLVED_PASS` or `NONCOMPLIANT`. An inconclusive re-audit appends a SUSPENDED→SUSPENDED transition.
* **D-14 Propagation.** The *direct* dependents in the static primitive graph (`medb/interfaces.py: PRIMITIVES`) get their own records with `propagated_from` set. Every transitive dependent beyond them is flagged `SUSPENSION_ADJACENT` and is **not** suspended.
* **D-15** When the parent record resolves `RESOLVED_PASS`, the propagated records resolve too. On `FAIL` they stay suspended.
* **D-16 Auditor role.** Auditor identities come from a list in config that is recorded at genesis. There is no authentication (see F-04). `resolve` and `record_audit_result` refuse any non-auditor, including `user`. `lift` is refused for **every** actor. Charter resolution raises `CharterResolutionUnavailable`. *(Update 2 Oct 2026, D-69: the config list is replaced. Auditors are now appointed only by the independent appointer's signed statements; `resolve`/`record_audit_result` require an active appointment. `lift` is still refused for everyone.)*
* **D-11 Audit-plane exemption.** Q-1 queries, export and integrity verification are registered as `plane="audit"`. They *read records about* suspended primitives and are not blocked by suspension, because resolution needs a re-audit and a re-audit needs the evidence path. See F-11. *Update 2 Oct 2026 (Gem's ruling on F-11):* still open, but now logged during suspension (D-66).
* **D-39 Integrity failure.** A broken chain is "records insufficient for audit", so the corresponding primitive is suspended as **UNDETERMINED** (Interpretation Rule). Stream-to-primitive mapping: `gov`/`suspension` → `governance.log`, `claims` → `claims.ledger`, `policy` → `policy.store`, `permissions` → `permissions.closure`, `corpus` → `corpus.ingest`, `delegation` → `delegation.execution`.
* **D-40 AUDIT_INDETERMINACY** suspends by default. This is configurable in `config.audit.suspend_on`; see F-08.
  *Update 2 Oct 2026 (Gem's ruling on F-08):* **corrected (this was a build divergence from spec II-C).** AUDIT_INDETERMINACY means *re-audit required*. It **never** suspends automatically. `record_audit_result` appends `REAUDIT_REQUIRED` to gov (`automatic_suspension: false`) and no suspension record is created. An inconclusive re-audit of an already-suspended record leaves it SUSPENDED and also logs `REAUDIT_REQUIRED`. The value was removed from the default `audit.suspend_on`, and `SuspensionRegistry` refuses any configuration that lists it.
* **D-18 Interface inventory** is *derived from code*: every guarded entry point is decorated with `@reaches(primitives...)`, and that decorator both registers the interface and enforces suspension.

### Context packages
* **D-20 Logged, not retained.** `CONTEXT_PACKAGE_ISSUED` records:
  * ids, versions and event hashes of the included claims,
  * the per-claim **template key**,
  * the rendering-config digest,
  * contradictions, unknowns, boundary,
  * the **full ranking record** (inputs, weights, scores, order),
  * a structure digest, built over references rather than content (so the log does not commit to content in a brute-forceable way).

  Rendered text is never stored. Reconstruction works from the ledger as of `issued_at` plus the config. The consumer helper `open_package` refuses packages past `expires_at`.
* **D-34 Modal symmetry.**
  * The proposition is rendered with one fixed grammar (`statement_format`), whatever its origin.
  * Epistemic status appears **only** as an explicit attribution prefix chosen by `confirmation`.
  * A self-check flags `SELF_ACCOUNT_HEDGED` (hedge words in the frame around a user self-account, but not inside the user's own words) and `INFERENCE_UNATTRIBUTED` (an inference with no status marker).
  * The builder **refuses to issue** an asymmetric package and logs the refusal.
  * The hedge lexicon is a coarse M0 heuristic.
* **D-32 Contradictions** are detected explicitly (`incompatible_with`) or implicitly (same subject and same single-valued predicate, from config, with different objects). Both sides are always included and marked `resolution: none (preserved)`. Contradictions with *withheld* claims are counted in the boundary without revealing content.
* **D-33 Ranking.** The default weights are relevance 1.0 and recency 0.1. Origin is **not** a ranking feature. Every input is recorded (`record_inputs: true`). See F-12.
* **D-35 TTL.** Default 60 minutes, capped at 1440.
* **D-49 Frames.** Frames are claims with predicate `frame`. They appear in the package's `frames` section, separate from the body claims.

### Q-1, self-description, export
* **D-12 Q-1 reads are not logged** to the governance log, so that querying never perturbs the evidence it reports (tested). *(Update 2 Oct 2026, F-11: still true for `gov`. Audit reads made while a suspension is active go to the separate `auditlog` stream, D-66, and `gov` is untouched; tested.)* Retrievals of claim **content** (`retrieve`, package build) *are* logged as `CLAIMS_RETRIEVED`.
* **D-19 Generated self-description.** `self_description` is built from the running objects: component classes and source-file sha256, the loaded config, policy digests, the interface inventory, the charter digest at genesis and now, and active suspensions. Nothing in it is hand-written prose. *(Update 2 Oct 2026, D-68: the `network` field had been a hand-written string, "none (local-first; no network code in substrate)", which became wrong when D-62 added anchoring. It is now generated.)*
* **D-17 Prohibition guard.** The permanent-prohibition guard is lexical (`persua`, `susceptib`, `manipulat`, `nudge`, `engagement_optim`). It is applied to purposes, inferred predicates and objects, ranking objectives and weight names, and action descriptions. It is coarse and **does not prove** non-manipulation.
* **D-41 Export** (`medb-export/1.0`) contains:
  * every event of every stream, verbatim,
  * surviving content with its salts,
  * materialised state,
  * a PROV-JSON view,
  * JSON Schemas and a README,
  * a **standalone stdlib verifier** that does not import MedB.

  Tests run the verifier in an isolated interpreter (`python -I`). It checks file digests, chains, commitments and cross-links, and independently replays the claim state.
* **D-50** Charter constants live in `medb/constitution.py`. No runtime API can modify them. `CHARTER_DIGEST` is written into GENESIS and reported by Q-1.

### Round 1 subject scaffolding (Step 3)
* **D-51 Variant mechanism.** Each subject is a combination of a config override and a `subject_components.py` binding file. **Every** subject, compliant or not, ships the same set of class names (`EvaluatorImpl`, `PolicyStoreImpl`, `RankerImpl`, `RendererImpl`, `ContextBuilderImpl`, `DelegationImpl`), so `self_description` cannot reveal which subjects are modified. Variants hook into neutral core extension points (`Evaluator._cumulative_exceeded`, `Evaluator._frequency_exceeded`, `ContextPackageBuilder._modal_findings`, `DelegationService._execute`, `Ranker.rank/features`, `Renderer.render`). These hooks exist in the core for every subject.
* **D-52 Blinding.** Envelopes leave out labels, scenario/driver code, `run_meta.json`, seeds, ground truth and pairing. Envelope codes are random (`E1-xxxxxx`), and the key exists only in `experiment/ground_truth/blinding_key.json`. Snapshots are named `snapshot-NN`, and the EXPORT log entries use the same neutral labels. A regex leak scan runs on every build and must report zero hits.
* **D-53 Residual pairing signal.** Subjects that share a workload produce structurally similar logs, so an auditor *could* infer which envelopes share a workload, even though no pairing information is included. X1 has no compliant control on its workload: a test runs that workload on the compliant bindings and shows escalation at the 13th invocation, but no envelope is produced for it. Fixing this (diversifying workloads, adding an X1 control envelope) is for the experimenter to decide.
* **D-54 Expected outcomes are provisional.** The builder proposed the ground-truth `expected_outcome` values. For the B family they are explicitly left for the experimenter to decide.
* **D-56 Seeded re-open.** Re-opening a seeded instance derives its id seed from `seed` and the event count, so ids never collide. This was a bug found while building envelopes, and it is now covered by a test.

### Local HTTP API, read-only web UI and interactive app
* **D-55 Server.** stdlib `http.server.HTTPServer`, which is **single-threaded**: requests are serialised, so one SQLite connection is safe (`check_same_thread=False`). No dependency was added; FastAPI was not justified. The server binds to **127.0.0.1 only**, and `make_server` refuses any other host.
* **D-57 Routing through the same mechanisms.** Every route is registered with `register_route` and appears in `interface_inventory()["routes"]`. Routes that reach primitives are also listed under those primitives' `interfaces` (e.g. `HTTP POST /api/ingest/corpus` under `corpus.ingest`). Capability-plane routes run the suspension check at the primitive *before* the handler. They then call the same in-process interfaces, which check again. Refusals map to HTTP: suspended → 423 (with the blocking record id), not authorised / permission / prohibition → 403. Q-1 routes are exactly the eight queries, and are audit-plane (D-11).
* **D-58 Authentication.** Each bearer token is bound to one actor (`user`, `reader`, `agent:coder`). Tokens live in `data/api_tokens.json` (mode 0600, gitignored, created on first run). `reader` is GET-only. `/api/delegation/evaluate` requires `action.agent == authenticated actor`. The actor of an API write is the token's actor, and the ledger/permission rules apply unchanged. For example, an agent token cannot assert a user self-account.
* **D-59 Evaluate = submit.** `/api/delegation/evaluate` goes through `DelegationService.submit`. Every evaluation is recorded, and an AUTHORIZED action is recorded as executed. No unlogged dry-run endpoint exists, because unlogged policy probing would bypass "the governance log records every action".
* **D-60 UI ledger reads are logged.** `GET /api/view/claims` and `/claim_history` read claim content, so they are capability-plane on `claims.ledger` and each one logs `CLAIMS_RETRIEVED` (`purpose: ledger_inspection`, actor = token actor). As a result they become unreachable while `claims.ledger` is suspended. The suspension registry and the governance log (Q-1) stay readable (audit plane).
* **D-61 Web UI.** Static HTML/JS served by the API. GET requests only. Rendering uses `textContent` only, with a Content-Security-Policy header. No forms and no write actions. Tests enforce all of this. *(Update 2 Oct 2026: still true for the read-only UI at `/`; the separate interactive app is D-67.)* *(Update 2 Oct 2026, evening, D-70: the read-only viewer is **removed** (`medb/webui/` and `/app.js` deleted) at Gem's request because the app supersedes it; `GET /` now redirects (302) to `/app/`.)*
* **D-67 Interactive app (`app/`, 2 Oct 2026). Not part of Round 1.** Round 1 excludes user-facing interfaces, so the app is kept out of `experiment/`, `subjects/` and the envelopes. No subject script, scenario or ground-truth file references it. ### Gem's rulings, implemented 2 Oct 2026
* **D-62 External anchoring (F-13).** `medb/anchoring.py` is the only module that imports network code. `Anchorer.anchor_heads(actor)` (`@reaches("governance.anchoring", "governance.log")`; actor must be `user` or `system`) works as follows:
  * It computes `heads = {stream: {seq, hash}}` over every stream except `anchors`, and `heads_digest = sha256(canonical(heads))`.
  * It sends **only** an RFC 3161 TimeStampReq containing that digest, a random nonce and certReq, over HTTPS only.
  * It stores an `ANCHOR` event in the hash-chained `anchors` stream: heads, digest, request digest, nonce, the raw TimeStampResp in base64, and a local check result. The event is mirrored into gov.

  Anchoring is **off by default** (`config.anchoring.enabled: false`, `tsa_url: null`) and raises `AnchoringDisabled` unless enabled. Nothing calls it implicitly. `verify_anchor` and the standalone verifier both check three things: the recorded heads match the chains, the digest is correct, and the receipt was granted and carries the digest as its message imprint. The TSA's CMS signature cannot be verified with the stdlib, so that check is done offline (`openssl ts -verify`), as documented in the export README. OpenTimestamps is not implemented: RFC 3161 gives one round trip and a self-contained receipt. *(Note 2 Oct 2026, evening: Gem ruled RFC 3161 only. OpenTimestamps is dropped as an option and no longer mentioned in code or docs; the original wording here and in F-13 is kept as history.)* Tests use a fake TSA client, and an autouse fixture refuses all non-loopback network access in the test suite. Exception to D-01.
* **D-63 Deferrability (F-02).** A decision is non-deferrable only if (a) the **user** passes `deferrable=False` when resolving, or (b) an `ENV_CONDITION` `deadline` or `outage` is currently true. The condition must be recorded by `environment` or `user`, and may be global or scoped with `matter=`. An agent-supplied `deferrable` on an action is **stripped and ignored**, and a `false` value is logged as `PROHIBITED_ATTEMPT` (`agent_set_non_deferrable`). The action itself is still evaluated normally. Deferrability is recorded on `ESCALATION_OPENED` with `deferrability_basis`, and re-derived at resolution time, because conditions may have been recorded since. The CU1 scenario now records an environment `deadline` for `token-exposure-response` instead of an agent flag; its outcome is unchanged.
* **D-64 Corpus WITHDRAW (F-05).** `Corpus.withdraw(corpus_id, actor="user", reason)` is user-only (`@reaches("corpus.ingest")`). It appends `WITHDRAW` to the corpus stream and mirrors it to gov. Content is **not** erased. The item is excluded from derivation closure, inference inputs, `retrieve` and packages (see D-09). There is no un-withdraw. To use the material again, the user re-ingests it as a new item.
* **D-65 Deletion choice (F-06).** `ClaimLedger.preview_delete(claim_id)` is user-only, logged as `CLAIMS_RETRIEVED` with `purpose: deletion_preview`, and returns every claim transitively `derived_from` the target. `delete(claim_id, destroy_derived=...)` accepts `"none"` (default, the previous behaviour: derived claims are kept but unusable), `"all"`, or a list drawn from the preview. Anything else raises `ValueError`. The DELETE body records `derived_listed`, `destroy_derived` and `derived_kept_unusable`. Each chosen claim gets its own content-destroying `DELETE` with `cascade_of`.
* **D-66 Audit-read log (F-11).** The audit plane stays open. While **any** suspension is active, each *outermost* audit-plane read (Q-1 methods, audit HTTP routes, export) appends an `AUDIT_READ` event to the hash-chained **`auditlog`** stream. Each event records the interface, the primitives, the reader (the API token's actor; `unspecified` for in-process calls without an actor) and the active suspension record ids. Nested reads, such as a route calling a Q-1 method, are logged once. `auditlog` is **not** written to or cross-linked into gov, so D-12 holds and Q-1 results are unperturbed. The verifier checks that the chain is intact, that no gov cross-link points at it, and that every entry references recorded suspensions. Integrity checks (`integrity_check`) are not audit-plane reads and still log `INTEGRITY_CHECK` to gov as before.
* **D-68 Generated network self-description (Gem's ruling, 2 Oct 2026).** Gem ruled that the self-description must report network code accurately, generated from the running code and config as D-19 requires, and that the Round 1 envelopes be regenerated. `Q1.self_description()["network"]` is now built by `medb/netscan.py`. It AST-scans every module in the `medb` package for imports of network-capable modules (`socket`, `ssl`, `http.client`/`http.server`, `urllib.request`, `requests`, …). The scan covers function-local imports too, such as anchoring's lazy `import urllib.request`. For each module it finds, it reports the imports, the source sha256 and the module's machine-readable `NETWORK_DECLARATION`. For `medb.anchoring` it also reports the live config: `enabled`, `method`, `tsa_url`, the default from `config/default.json` (`default_enabled: false`) and a config digest. The result at this commit: **outbound** network code is only `medb.anchoring` (RFC 3161 TimeStampReq over HTTPS; sends one SHA-256 digest of the stream heads plus a nonce, no content; never called implicitly; off by default). There is also one **inbound** module, `medb.api`, the stdlib HTTP server for the local API/UI (D-55), which binds to `127.0.0.1` only and makes no outbound calls. This is reported because it is network code too. So "no other module has network code" holds for outbound connections, not for the loopback listener. A module with network imports but no declaration is listed under `undeclared`, and tests require that list to be empty, so adding network code without declaring it fails the suite. All Round 1 runs and E-1 envelopes were regenerated (`subjects/run_all.sh` → `build_envelopes.py`). The leak scan found 0 hits, and a new blinding key was committed. The §6.8 subject matrix was identical to the run before the change. This supersedes D-67's note that `self_description` was byte-identical to 152598a: only the `network` field changed.

### Gem's changes, 2 Oct 2026 (evening)
* **D-69 Auditor appointment by an independent appointer (F-04, Gem's ruling).** New module `medb/auditors.py`, new primitive `audit.appointment` (depends on `governance.log`) and a new hash-chained stream `appointments`, cross-linked into gov.
  * *Appointer fixed at genesis.* `config.appointer = {id, key_fingerprint, method: "hmac-sha256", verify_key_file}` is recorded in the GENESIS entry and is the only appointer. Nothing at runtime can change it: there is no API or in-process method to set it, and a later config naming a different appointer is refused and logged as `PROHIBITED_ATTEMPT` (`appointer_rebind_refused`). For a database created **before** F-04 (whose genesis has no appointer), the first configured appointer is bound **once** (`APPOINTER_BOUND`, trust on first use) and is equally unchangeable after that. With no appointer configured (the default), no one is an auditor.
  * *Statements.* The appointer issues `APPOINT {auditor_id, appointment_id, nonce, issued_at, expires_at?, scope?}` and `REVOKE {appointment_id, nonce}` statements, signed with HMAC-SHA256 over the canonical JSON. `AuditorRegistry.submit_statement(statement, signature, actor)` verifies the signature with the key in `verify_key_file`, whose SHA-256 must equal the genesis fingerprint. It also checks the appointer id, replay (statement hash and nonce), the `auditor:` id prefix (`user`/`system`/`reader` can never be appointed), duplicate appointment ids, revocation of unknown appointments and unknown types. The carrier (any token, via `POST /api/auditors/statement`) gains nothing; the event's actor is the appointer id, and the carrier is recorded. Every refusal is a `PROHIBITED_ATTEMPT` and raises `NotAuthorized`.
  * *User and system refused.* `AuditorRegistry.appoint(...)` exists only to refuse: `user_cannot_appoint_auditor`, `system_cannot_appoint_auditor`, or `unsigned_appointment` for anyone else, each logged as `PROHIBITED_ATTEMPT`.
  * *Auditor actions need an active appointment.* `SuspensionRegistry.resolve` and `record_audit_result` call `is_auditor(actor)`, which requires an appointment that is recorded, unrevoked and unexpired. Rules for outcomes are unchanged (PASS/FAIL/UNDETERMINED/AUDIT_INDETERMINACY; F-08: AUDIT_INDETERMINACY requires re-audit and does not suspend).
  * *Migration.* `config.auditors` is removed from `config/default.json` and from `self_description` (D-19), which now reports `auditor_appointment: {appointer, active_auditors, method}`. A database whose genesis config still lists `auditors` gets one `LEGACY_AUDITORS_RETIRED` gov entry on open; those ids stop being auditors unless appointed. Existing records are untouched.
  * *M0 limitation: HMAC is symmetric.* The stdlib has no asymmetric signatures, so MedB's verify key is the appointer's secret. Anyone who can read `verify_key_file` on the MedB machine could forge appointments. The file should be readable only by the appointer and the MedB process (`tools/appointer.py keygen` writes it 0600). Asymmetric signatures (e.g. Ed25519) would remove this and are left for later.
  * *Appointer tool.* `tools/appointer.py keygen|appoint|revoke` is run by the outside party: it creates the key and `data/appointer.json`, and prints signed statement bodies for `/api/auditors/statement`. `python3 -m medb.api` loads `data/appointer.json` if present (`--appointer PATH`).
  * *Auditor tokens and the auditor desk.* `data/api_tokens.json` gets an `auditor:external-1` token (`--auditor ID` to choose). An `auditor:*` token may use only audit-plane, meta and static routes; anything else gets 403 and a `PROHIBITED_ATTEMPT` (`auditor_outside_audit_plane`). Export is therefore not available to auditors (it bundles claim content). A token for an unappointed id can read the audit plane but cannot record anything. New routes: `GET /api/view/appointments`, `GET /api/view/audit_evidence?record_id=` (record, transitions, related gov entries, chain checks; no claim content), `POST /api/audit/result` and `POST /api/audit/resolve`. The two POSTs are **audit plane** and so are not blocked by a suspension; this is a deliberate exemption like `integrity_check` (D-11/D-66), because re-audit is the only route out of a suspension. The app has an *Auditor desk* screen (suspension list, evidence, re-audit outcome, audit-result form); capability screens are hidden for auditor tokens.
  * The app and its routes stay out of Round 1 (D-67). `self_description` and the in-process inventory changed (new primitive, stream, component and the `auditor_appointment` field), so the envelopes were regenerated. The leak scan found 0 hits and the §6.8 matrix was unchanged.
* **D-70 App cuts and the delegation grant manager (Gem's request).** (a) The read-only viewer (D-61) is removed: `medb/webui/` and `/app.js` are deleted, and `GET /` redirects to `/app/`. * **D-77 OAuth flows, tokens and disconnect.** `medb/integrations/oauth.py` and `sync_tokens.py`.
  * *Flows.* Google: installed-app loopback redirect (`127.0.0.1:<ephemeral>`) + PKCE S256 + `state`. GitHub: device flow. Facebook: login dialog with loopback redirect `http://localhost:<redirect_port>/` (default 8767) + `state`; Graph version configurable (default v26.0). The one-shot listener (declared `loopback` in `netscan`) only stores code/state. The exchange runs on the API thread when the app polls `connect_poll`, so the database is written from one thread only.
  * *Client registrations.* The user supplies them in `data/sync_clients.json` (gitignored), **not** in the config, which is recorded at GENESIS and exported.
  * *Scopes.* Read-only only: `gmail.readonly`, `calendar.readonly`, `contacts.readonly` (+ `openid email` to name the account), GitHub `read:user`, Facebook `public_profile,user_posts`. A token whose granted scopes go beyond `ALLOWED_SCOPES` is refused and not stored.
  * *Tokens.* Stored in `data/sync_tokens/<provider>.json` (dir 0700, file 0600, atomic write, gitignored). They are **not encrypted** (F-29; no stdlib crypto, none invented). Tokens appear only in the `Authorization` header (and the provider's token/revoke form bodies); the governance log, `sync` stream, status, outbox, export and self-description see only `public()` metadata (account id, scopes, expiry). Tests plant access/refresh tokens, client secrets and a device code and search the DB file, every event body, gov, export, outbox, self-description, status responses, config and captured stdout/stderr/logs.
  * *Account id.* Google from the id_token received directly over TLS (not signature-checked, F-34), GitHub from `/user`, Facebook from `/me`, local profiles from the directory name.
  * *Disconnect.* `SyncManager.disconnect` is user only and deletes the local token (one Google token serves all three Google services). Optional best-effort remote revoke for Google/Facebook; GitHub is revoked by the user on github.com. It is on a new **revocation plane**: `@reaches("integrations.sync", plane="revocation")` / route plane `revocation`, not blocked by suspension, because it only removes capability.
* **D-78 Sync semantics, actors, routes, app, scheduler.** `medb/integrations/livesync.py`, `SyncManager.sync` (`@reaches("integrations.sync", "corpus.ingest", "permissions.closure")`).
  * *Grant first.* An active `ingest` grant must cover source `sync:<service>`, the service scope (`correspondence`, `calendar`, `contacts`, `code`, `social`, `browsing`; configurable) and sensitivity **high**. It is checked before any API call; items are ingested at sensitivity high.
  * *Provenance per item.* `service`, `provider`, `account_id`, `endpoint`, `remote_id`, `version` (etag / history id / updated time), `run_id`, `response_sha256`, `supersedes_corpus_id`, `third_party_content` (+ mail details or cookie metadata).
  * *Incremental and idempotent.* Incremental via Gmail `historyId` (404 → full re-list), Calendar/People `syncToken` (410 → full resync), GitHub `since` + events ETag, Graph `since`, browser last-visit cursors. The dedup index is rebuilt from corpus provenance: same remote id and version → skipped; changed version → new item superseding the old. Cursors live in `RUN` events of the hash-chained `sync` stream (mirrored into gov). A failed or truncated (`max_items_per_run`) run does not advance the cursor.
  * *Remote deletions.* Recorded as `REMOTE_DELETION` (once per object), with a `SYNC_REMOTE_DELETION` outbox notification; never erased or auto-withdrawn (F-32). Failed runs notify `SYNC_FAILED`.
  * *Local browsers.* Files (+wal/shm) are copied to a 0700 temp dir, opened `mode=ro`, and the copy is removed in `finally`; the profile is untouched. Cookies use the importer's `COOKIE_SQL` (D-72): no names, no values, per-domain count and times only. The planted-cookie test now also covers the live path.
  * *Actors.* Connect / connect-poll / disconnect: `user` only. Run: `user`, or `system` for the user-configured schedule. `agent:*`, `inference:*`, MCP actors, `reader`, `auditor:*` are refused (`PROHIBITED_ATTEMPT`) before any network call. No MCP tool exists for sync, and the MCP header is refused even with the user token. Assistants also still cannot import, confirm, grant or resolve (D-74).
  * *Routes* (`api_integrations.py`, app-only like D-75). Audit: `GET /api/sync/status`, `GET /api/view/sync_runs`. Capability, user only: `POST /api/sync/connect`, `/connect_poll`, `/run` (`{service}` or `{all}`); 423 when `integrations.sync` (or `corpus.ingest` for runs) is suspended. Revocation plane: `POST /api/sync/disconnect`. Errors: disabled / no client → 409 `integration_disabled`; refusals → 422 `sync_refused`; `HostNotAllowed` → 403; provider errors → 502. Gov kind `SYNC_REFUSED`.
  * *App.* The Integrations screen has a *Live account sync* table: per service enabled/connected, account, last sync, items, last-run counts, error, hosts, and (user token) Connect… (opens the provider sign-in or shows the device code and polls) / Sync now / Disconnect (confirm), plus Sync all.
  * *Scheduler (off by default).* `integrations.sync.schedule {enabled, interval_minutes}` makes `python -m medb.api` serve via `handle_request()` and run due syncs between requests on the same thread, as `system`. Alternatively, `tools/medb_sync.py status|run [--service|--all]|connect` runs from cron against the loopback API with the user token.
  * *Tests.* Fake providers through the injected transport only; the autouse no-network fixture still holds, and only the loopback listener and API are touched. Round 1 is unaffected: the subjects never enable sync. Envelopes were regenerated because the source and self-description changed.
